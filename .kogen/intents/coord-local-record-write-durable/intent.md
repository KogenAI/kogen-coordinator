# Write local records and index restores durably

Slug: coord-local-record-write-durable
Model: not applicable — each call is one write-flush-rename procedure with no state machine of its own; the rename provides the old-or-new atomicity and concurrent writers only need distinct temp files
Acceptance:
- .kogen/intents/coord-local-record-write-durable/acceptance.feature
- features/steps/coord-local-record-write-durable__driver.js

Kogen's `.kogen/local` records are written by `project.WriteJSONAtomic(path string, v any) error` (`project/facts.go`; package facts use it through `WritePackageFacts`). Today it writes the fixed name `<path>.tmp` with `os.WriteFile` and renames it over `path`, without flushing the file to stable storage. Two writers of the same record therefore share one temp file (their bytes can interleave, or one writer's rename fails with "no such file or directory" because the other already renamed the shared temp), and a failed write of the temp file leaves `<path>.tmp` behind. `git.Repo.RestoreIndex(backup string) error` (`git/index.go`) already uses a unique temp name (`index.kogen-restore-<random hex>` in the Git directory) but writes it with `os.WriteFile` and renames it without a flush. After a power loss or kernel crash, a renamed file can be empty or short.

After this change:

- `project.WriteJSONAtomic` keeps its signature and its bytes: the file holds `EncodeJSON(v)` followed by one `\n`, exactly as today. It creates its temp file in the target's folder (`filepath.Dir(path)`) under a unique name, never the fixed `<path>.tmp`: for example `<base>.tmp-<16 random hex digits>` opened with `os.O_WRONLY|os.O_CREATE|os.O_EXCL` and permission `0o666`, so the record keeps today's permission (0666 less the process umask, `0644` under umask 022). It writes the bytes, calls `durable.Sync` on the temp file exactly once, closes it, then renames it over `path`. On every failure after the temp file was created (write, sync, close or rename) it closes the file if still open, removes the temp file and returns the failure's error; the existing record is left as it was. A successful call leaves no temp file. A reader still sees only the old file or the complete new one. It does not flush the folder: one call makes exactly one `durable.Sync` call, on the temp file.
- `git.Repo.RestoreIndex` keeps its signature, its temp name (`index.kogen-restore-<random hex>` in the Git directory), the `restore index: ` error prefix on a failed rename, and the mode rule: the restored index has the permission of the index it replaces (`0644` when there is none), set exactly. It writes the temp file through an open file, sets the mode, calls `durable.Sync` on it exactly once, closes it and renames it over the index; on every failure after the temp file was created it removes the temp file. No folder flush.
- Both use the one shared flush helper `durable.Sync`, so a test binary that called `durable.SkipSyncInTests()` still switches the flush off.
- New exported test seam in package `durable` (`durable/durable.go`): `func ObserveSyncInTests(fn func(f *os.File))`. From that call on, every call of `durable.Sync(f)` first calls `fn(f)` with the same `*os.File`, then flushes it with `f.Sync()` and returns its error (or, after `SkipSyncInTests`, skips the flush and returns nil); fn is called whether or not syncing is skipped. A later call replaces fn; `ObserveSyncInTests(nil)` removes it. It is safe to call concurrently with `Sync` (store fn atomically, like `skip`). Only Go test files and test drivers call it; the kogen program never does. `durable.Sync` and `durable.SkipSyncInTests` otherwise keep their behaviour; the contract item `durable-skip` is unchanged.

Out of scope and unchanged: the provenance writer (`project.PublishSource`, already flushed), the run store (`durable.RunStore`), `project.WriteApproval`, `project.RestoreSource`, `git.Repo.SaveIndex`, and stale `<path>.tmp` files left by earlier versions (they are not cleaned up). No golden or recorded hash changes.

Acceptance builds (`go build -o`) and runs a Go driver that the step file generates in a temporary folder of the module; it calls `project.WriteJSONAtomic`, `project.EncodeJSON`, `git.Open`, `Repo.GitDir`, `Repo.SaveIndex`, `Repo.RestoreIndex` and, through a small `seam.go`, `durable.ObserveSyncInTests`, and at each observed flush records the flushed file's name, its bytes and the target's bytes at that moment. On a tree without `durable.ObserveSyncInTests` (today's), the build fails with `undefined: durable.ObserveSyncInTests` and the step rebuilds with a do-nothing seam, so the driver runs and observes no flush; every scenario then fails at its observation. The write-failure case limits the driver process's file size to 64 bytes with `RLIMIT_FSIZE` (Go ignores `SIGXFSZ`, so the write returns an error); the sync-failure case has the observer close the temp file, so the following `f.Sync()` fails.

## Decisions
- Every atomic local write flushes the file's contents before the rename, through the one shared flush helper `durable.Sync`, so test binaries can still switch it off (source: request)
- Every atomic local write uses a unique temp name in the target's folder and removes the temp file on every failure path (source: request)
- The restore of the user's index flushes its temp file before the rename (source: request)
- A reader still sees only the old file or the complete new one; record bytes are unchanged from today's output for the same input; a restored index keeps the mode of the index it replaced (source: request)
- The flush counter is the test seam `durable.ObserveSyncInTests`; one record write and one index restore each make exactly one `durable.Sync` call, on the temp file, before the rename (source: request)

## Source comparison
- Fixed `<path>.tmp` temp name shared by concurrent writers: replaced by a unique temp name in the target's folder (request "Need"; prose bullet 1; scenario "Two concurrent writes of one record leave one complete input and no temp file").
- No flush in `WriteJSONAtomic`: replaced by one `durable.Sync` of the temp file before the rename (request "Need"; scenario "One record write flushes its temp file before the rename and keeps today's bytes and mode").
- Temp file left behind on failure, removed on every failure path (request "Problem" and "Need"): scenarios "A failed write of the temp file returns an error and leaves no temp file in the folder" (today leaves `facts.json.tmp`), "A failed flush returns an error, keeps the old record and leaves no temp file in the folder" and "A failed rename returns an error and leaves no temp file in the folder".
- Index restore without flush: one `durable.Sync` of its temp file before the rename (request "Need"; scenario "An index restore flushes its temp file before the rename and keeps the index's mode").
- Synthetic acceptance "write a record twice, concurrently, from two goroutines on a temp folder: final file is valid JSON equal to one of the two inputs, no `.tmp` or temp-named file remains": the concurrent scenario, repeated in 200 fresh folders, also requiring both writes to succeed and to flush two different temp files in the folder.
- Synthetic acceptance "make the rename fail (target is a non-empty directory): returns an error, leaves no temp file": the rename-failure scenario; the directory and its file `keep` stay intact.
- Synthetic acceptance "with the flush counter in the test seam, one record write calls the flush helper on the temp file before the rename; one index restore does the same": the record-flush and index-restore scenarios, observing the flushed temp file's complete new bytes while the target still holds its old bytes.
- Synthetic acceptance "mode of a restored index equals the mode of the index it replaced; record bytes unchanged": index-restore scenario (replaced index mode `0600`) and record-flush scenario (exact bytes `{"a":[1.50,true,null],"m":{"a":"1","b":"2"},"z":"é<>&"}` plus newline, mode `0644` under umask 022), plus the existing golden and `EncodeJSON` tests.
- "Power loss or kernel crash" is not simulated; the flush-before-rename order is what acceptance observes.

## Tests
- `durable.ObserveSyncInTests` calls fn with the file on every `Sync`, also after `SkipSyncInTests`, and nil removes it: new test in `durable` (unit)
- `SkipSyncInTests` still switches the flush off: existing contract `TestDurableSyncIsSkippedInTests` (existing)
- `WriteJSONAtomic` flushes its temp file once through `durable.Sync` before the rename, the target still holding its old bytes at that moment: new test in `project/facts_test.go` with `durable.ObserveSyncInTests` (removed in `t.Cleanup`, not `t.Parallel`) (integration)
- Two concurrent `WriteJSONAtomic` calls on one record both succeed, leave one complete input and only the record in the folder: new test in `project/facts_test.go`; update `TestWriteJSONAtomicNeverTearsUnderConcurrentReaders` to check that the folder holds only the record instead of checking `path + ".tmp"` (integration)
- A failed rename (target is a non-empty directory) returns an error and leaves no temp file: new test in `project/facts_test.go` (integration)
- A failed flush (the observer closes the temp file) returns an error, keeps the old record and leaves no temp file: new test in `project/facts_test.go` (integration)
- A failed write of the temp file returns an error and leaves no temp file: acceptance scenario "A failed write of the temp file returns an error and leaves no temp file in the folder" (the file-size limit is process-wide, so it stays in the separate driver process) (scenario)
- Record bytes are unchanged for the same input: existing `TestEncodeJSON`, `TestWritePackageFactsMatchesElixirLocalFactsPackage` and the facts golden (existing)
- `RestoreIndex` flushes its temp file once through `durable.Sync` before the rename: new test in `git/index_test.go` (integration)
- A restored index keeps the replaced index's mode and leaves no `index.kogen-restore-*` file: existing `TestIndexCustodyRestoresWhatTheUserStaged` (existing)

## Feasibility
- Scratch copies outside the repository (external-session observations, not Kogen probe records): on today's code with the do-nothing seam the driver reported 0 flushes in every case, a leftover `facts.json.tmp` after the write failure, a successful write despite the closed file, and 61 to 71 of 200 concurrent rounds failing to rename the shared `facts.json.tmp`; with a candidate implementation it reported the observations the feature expects.
