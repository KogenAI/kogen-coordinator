# Stop routing between steps when cancelled

Slug: coord-route-honours-cancellation
Model: not applicable — the change adds one context check before each step call of two existing linear routines; it introduces no state, retry or interacting rule beyond the step order the existing tests already pin
Acceptance:
- .kogen/intents/coord-route-honours-cancellation/acceptance.feature
- features/steps/coord-route-honours-cancellation__driver.js

`route.Cycle[E, A](ctx, s, builderPass) (feedback string, landed bool, err error)` and `route.Resume[E, A](ctx, s, stage) error` (`route/route.go`) pass `ctx` to each step of `route.Steps` but never look at it themselves. Today a run cancelled (an interrupt, or a passed deadline) while a step is returning is noticed only if that step happens to check, so the cycle goes on to start the next step, such as a review or a commit, after the run was told to stop.

After this change, immediately before calling each step that takes a context (`Verify`, `Review`, `Commit`, `Continue`, `Fresh`, `Approved`), `Cycle` and `Resume` check `ctx.Err()`. When it is non-nil they return it right away, unwrapped (`context.Canceled` with the text `context canceled`, `context.DeadlineExceeded` with the text `context deadline exceeded`), and no further step starts. `Cycle` then returns `("", false, ctx.Err())`, as it returns any step error today; `Resume` returns `ctx.Err()`. This includes the first step: an already cancelled context starts no step at all.

- `Cycle`: check before every `Verify` (also the restart after a drifted approval), before `Review` and before `Commit`.
- `Resume`: check before `Approved` and the commit of a `commit_failed` checkpoint; before `Fresh`, `Review` and `Commit` of a `review_only` checkpoint (or a review its reviewer cannot continue); before `Continue` and `Commit` of a continuing review. After a drifted commit `Resume` calls `Cycle` as today, whose check before `Verify` returns the context error; `Resume` returns that error (not the `candidate changed after review in a resumed commit` error).
- `Continuable()` takes no context and is not a step; it is called as today.

Boundaries:
- A commit already in progress is not interrupted by this check: there is no check after a step returns. A `Commit` that returns not drifted, with no error, during which the run was cancelled, yields `("", true, nil)` from `Cycle` and `nil` from `Resume`. A resumed `commit_failed` commit that succeeds returns `nil`.
- A red verification returns its feedback as today (`(feedback, false, nil)`), even when the run was cancelled during that `Verify`: no step follows a red candidate, so there is no check to make.
- Step errors are returned as today and take precedence: the check runs only before a step is started.
- Uncancelled runs behave exactly as today, including the order of steps, the `builderPass` of each `Verify`, the restart after a drifted approval and the resumed-commit error. The signatures of `route.Steps`, `Cycle` and `Resume`, the stage constants and the contract suite (`contract/route_test.go`, `contract/README.md`) are unchanged.
- The doc comments of `Cycle` and `Resume` state the check (between steps, never interrupting a step).

Acceptance builds (`go build -o`) and runs a Go driver that the step file generates in a temporary dot-prefixed folder of the module (removed when the acceptance process exits). The driver drives a scripted fake `route.Steps[string, string]` whose step calls are traced in order with the trace lines of `route/route_test.go` (`verify builder=yes|no`, `review <evidence>`, `continue`, `fresh <stage>`, `approved`, `commit <approval>` with ` (no restart)` when `restart` is false). The fake cancels its context inside a chosen step call (`context.WithCancel`), or for the deadline case waits inside `Verify` for a 100 ms `context.WithTimeout` to pass. Cycle cases call `route.Cycle` with `builderPass` true; Resume cases use a reviewer that can continue its session.

## Decisions
- Before starting each step (verify, review, commit, continue, fresh, approved) the cycle and resume check the context (source: request)
- A cancelled context returns its error right away and no further step starts (source: request)
- A commit already in progress is not interrupted by this check (source: request)
- Uncancelled runs behave exactly as today, including the order of steps and the restart after a drifted approval (source: request)

## Source comparison
- Request "Problem" (a cancelled run goes on to the next step unless that step checks): replaced by the check before each step call (prose, second paragraph and its bullets).
- Request "Need", interrupt and deadline: scenarios with `context.WithCancel` cancellation (`context canceled`) and "A run whose deadline passes during Verify reviews nothing and returns the deadline error" (`context deadline exceeded`).
- Synthetic acceptance "cancel the context inside Verify (which returns green); Review and Commit are never called and the cycle returns the context error": scenario "A run cancelled while Verify returns green reviews and commits nothing" (trace `["verify builder=yes"]`, error `context canceled`, landed false).
- "Cancel inside Review: Commit is never called": scenario "A run cancelled while Review returns commits nothing".
- "Cancel inside Commit that returns not drifted: the result is landed, with no error": scenario "A commit in progress when the run is cancelled lands" (landed true, error "").
- "Cancel after a drifted commit: no second Verify starts": scenario "A run cancelled during a drifted commit starts no second verification" (the cancel happens inside the drifted Commit, before the restart's Verify).
- "The same four cases for resume from a commit-failed, a review-only and a continuing stage": review_only covers all four (cancel inside Fresh, the step before Review, as the Verify analogue; inside Review; inside a not-drifted Commit; inside a drifted Commit). The continuing stage has no Verify/Fresh step: cancel inside Continue (its review), inside a not-drifted Commit and inside a drifted Commit. A commit_failed resume has neither a review nor a restartable, drifting commit (with `restart` false a drift is the phase's refusal, never a new cycle): cancel inside Approved (Commit never called) and inside its commit (returns nil). Each stage also has an already-cancelled-context scenario (no step starts).
- "With no cancellation, the call order for green, red and drifted-once cases equals the order of the existing tests": scenarios for cycle-green, cycle-red and cycle-drifted-once with the trace lines of `route/route_test.go` (drifted-once: the drift order of `TestRouteCycleAndResume` in `contract/route_test.go`); the existing route and contract tests stay unchanged and passing.
- Not in the request, decided here: a red verification during cancellation still returns its feedback (scenario "A red verification during cancellation still returns its feedback, starting no step"), because the check is only before starting a step.

## Tests
- `Cycle` checks the context before Verify, Review and Commit and returns `ctx.Err()` with no further step (cancel inside a green Verify; inside Review; already cancelled; a passed deadline): new tests in `route/route_test.go`, extending the test fake there to cancel inside a chosen step call (unit)
- A commit in progress is not interrupted (cancel inside a not-drifted Commit lands with no error) and a red Verify still returns its feedback: new tests in `route/route_test.go` (unit)
- Cancellation inside a drifted Commit starts no second Verify: new test in `route/route_test.go` (unit)
- `Resume` checks before each of its steps for the commit_failed, review_only and continuing stages, lets a commit in progress finish and, after a drifted commit, returns the context error without starting a Verify: new tests in `route/route_test.go` (unit)
- The requested behaviour through the public `route.Cycle`/`route.Resume` entry points in a separate program: acceptance scenarios with the generated driver (scenario)
- Uncancelled routing is unchanged (order of steps, restart after drift, resumed-commit error): existing `TestCycle*`, `TestResume*` in `route/route_test.go` and `TestRouteCycleAndResume` in `contract/route_test.go`, unchanged (existing)
