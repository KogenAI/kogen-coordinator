# Add a test-only flag to regenerate golden files

Slug: k-golden-update-coordinator
Model: not applicable — a boolean test flag chooses, per test run, between comparing and writing recorded outputs; there is no persistent workflow or interacting state
Acceptance:
- .kogen/intents/k-golden-update-coordinator/acceptance.feature
- features/steps/golden_update.js

Give this repository one documented, test-only way to regenerate its golden files: `go test ./... -update`. The goldens are `project/testdata/golden.json`, `project/testdata/facts-golden.json` and `project/testdata/parity.json`. Their golden tests are the existing tests that compare current Go output with a recorded output in those files: TestConfigMatchesElixir, TestRenderMatchesElixir, TestYAMLMatchesElixir, TestGherkinMatchesElixir, TestIntentCheckMatchesElixir, TestIntentReadMatchesElixir and TestDetectMatchesElixir (`project/golden_test.go`); TestEncodeJSONMatchesElixirJSONEncode and TestWritePackageFactsMatchesElixirLocalFactsPackage (`project/facts_test.go`); TestSourceComparisonMatchesElixir, TestConfigDigestMatchesElixirTermToBinary and TestCaptureSourceMatchesElixirFileForFile (`project/provenance_test.go`); and TestIntentHashMatchesElixir (`project/parity_test.go`). Keep these test names.

Without the flag, nothing changes. Every golden test makes the same comparisons, fails on the same drift with the same messages, and writes no file.

With the flag, each golden test runs its usual comparisons. A recorded output that would fail its comparison is replaced by the current code's actual output, recorded in the form the test reads back, so a follow-up run without the flag passes. Recorded outputs that still pass keep their recorded values. Recorded inputs (texts, files, overlays, slugs, state, the Elixir root named by `repo.refine.ref.path`) are never rewritten. As a result:
- A golden file with no drifted value is not written and stays byte-identical. This also holds for the Elixir results that only pass through the test-side normalizations (`openModelSelection`, `elixirConfig`, `emptyLists`, the `here` root substitution, the card hash substitutions).
- A file with drift is rewritten whole as compact JSON with a final newline, using the package's existing `EncodeJSON`. Probed: re-encoding the decoded `facts-golden.json` and `parity.json` with `EncodeJSON` reproduces them byte-for-byte. `golden.json` gets the same values, but some object keys come out in a different order.
- Values that receive a fresh path or hash on each run must be recorded so that the follow-up comparison passes. Examples are the refined receipts, receipt folder files and card in TestCaptureSourceMatchesElixirFileForFile, and the checkout id in the package facts. For instance, record a receipt in terms of the recorded Elixir root that the test's `here` substitution reads back.
- Several tests update `golden.json` and `facts-golden.json` one after another, and every one of those updates must survive. When a write fails, the test fails.
- In update mode, a golden mismatch is recorded instead of failing the test. A test that today stops at its first golden mismatch, such as the `t.Fatalf` on the captured receipt in TestCaptureSourceMatchesElixirFileForFile, continues so its later recorded outputs are checked and recorded too. Non-golden assertions keep failing the test as today, and so do the guards against an empty or truncated golden: TestGoldenIsCurrent, the minimum case counts, and "golden is inconsistent". When golden drift is the only problem, `go test ./... -update` exits 0.

Register the flag as a boolean named `update`, only in `_test.go` files. Register it in every package of this module that has tests (`git` and `project` today), so that `go test ./... -update` is accepted everywhere. In `git` it has no effect, because `git` has no goldens. All golden tests share one update path, for example one helper in a `project` `_test.go` file. No non-test package imports `flag`. The kogen binary gets no new CLI command, flag, config key or environment variable, and no environment variable switches update mode. Keep the Elixir generators `project/testdata/golden-gen.exs` and `project/testdata/facts-gen.exs` as provenance of the original results. No product behavior, timeout, dependency or test fixture is added or changed.

Document the flag in README.md's Testing section with the literal command `go test ./... -update`. Say when to use it: after a deliberate change to an output a golden records, or to resolve a conflict in a golden on the combined tree during delivery. Say what to do after it: review the golden diff (`git diff -- project/testdata`), then run `go test ./...` without the flag and the full checks. Recorded bytes and hashes are never edited by hand. Update the comment beside each golden loader or test (`golden.json`, `facts-golden.json`, `parity.json`) to say what that golden holds:
- the recorded inputs and their recorded results, originally produced by the Elixir Kogen;
- that `-update` records current Go output only for drifted values;
- that changing a recorded value is a deliberate, reviewed change. This applies above all to the hash-pinned approval hashes in `parity.json`, the config digests and contract hashes in `facts-golden.json`, and the main-Elixir results in `golden.json` that `openModelSelection` normalizes.

## Decisions
- The documented update command is `go test ./... -update`. The flag is a Go test flag registered only in `_test.go` files of each tested package. It is never a kogen CLI command, flag, config key or environment variable. (source: request)
- Without the flag, every golden test compares and fails exactly as today and writes nothing. With the flag, golden tests write drifted recorded outputs from the current code's actual output, and a follow-up run without the flag passes. (source: request)
- A golden is rewritten only for values that drifted. Matching recorded values, including the Elixir-produced results, stay as recorded, and an update on a matching tree writes no file. This way, changing a deliberate baseline always appears as a minimal, reviewable diff. (source: request)
- Covered goldens: the two files the request lists, plus the hash-pinned `project/testdata/parity.json`, whose approval hashes TestIntentHashMatchesElixir compares like the others, so the update path covers all golden tests. (source: request)
- README.md's Testing section documents when and how to use the flag, and each golden's test file says what that golden holds. (source: request)

## Tests
- Without the flag, a drifted golden still fails its existing tests and nothing is written: acceptance scenario 2 drifts golden.json, facts-golden.json and parity.json values in a scratch copy and requires exactly the 8 owning tests to fail with unchanged files (regression)
- With the flag, drifted values are rewritten from actual output, matching values and inputs are kept, and the follow-up run passes without writing: acceptance scenario 2 requires exit 0, all three goldens equal to the checkout's as JSON, then a passing, write-free `go test -count=1 ./project` (integration)
- An update on a tree whose goldens match writes nothing, and every test package accepts the flag: acceptance scenario 1 runs `go test -count=1 ./... -update` in a scratch copy and requires exit 0 with no changed file (integration)
- The flag stays test-only: acceptance scenario 1 requires that no package's non-test files import `flag` (`go list ./...`) (integration)
- README.md documents `go test ./... -update`: acceptance scenario 1 checks the literal command in README.md, and review checks the when-to-use text and the per-golden comments against the outcome prose (scenario)

## Feasibility
- On the unchanged tree, `go test -count=1 ./...` passes (git 21 s, project 3 s), and `go test -count=1 ./... -update` fails in both `git` and `project` with `flag provided but not defined: -update`. That is the expected missing-feature red of both scenarios. (probe: scratch copy)
- Re-encoding the decoded goldens with the package's `EncodeJSON` plus a final newline reproduces `facts-golden.json` and `parity.json` byte-for-byte. `golden.json` differs only in the key order of some objects (first at byte 69375). (probe: scratch test in a copy)
- On the unchanged tree, with the 8 drifted values, `go test -count=1 ./project` exits 1, reports exactly the 8 top-level tests listed in scenario 2 as `--- FAIL: TestName (…)`, and writes nothing. The acceptance steps observed that real output. With a no-op `update` flag registered in both test packages and the command added to README.md, scenario 1 passed and scenario 2 failed only at the update run. (probe: cucumber in a scratch copy)
