# Serialize run record writes per run ID

Slug: coord-run-store-concurrent-append
Model: not applicable — the change puts a per-run-ID mutual exclusion around the existing read-change-replace of `Append` and `Finish`; it adds no state of its own beyond "lock held or not", which the kernel's flock owns
Acceptance:
- .kogen/intents/coord-run-store-concurrent-append/acceptance.feature
- features/steps/coord-run-store-concurrent-append__driver.js

`durable.RunStore` (`durable/run_store.go`) keeps one JSON record per run ID at `<root>/<id>.json`. Today `Append(id, event)` and `Finish(id, outcome, reason, evidence)` each read the whole record, change it in memory and replace the file (temp file, `durable.Sync`, rename, directory sync) with no coordination. Two goroutines or processes writing the same run at once both read the same old record, and the later replacement silently drops the earlier writer's event, or a `Finish` summary overwrites an event added meanwhile. Nothing reports the loss.

After this change, the read, change and replace of one run record is serialized per run ID across goroutines and processes:

- The lock is an exclusive advisory `flock` (`syscall.Flock`, `LOCK_EX`, as `git/lock.go` already uses on darwin and linux) on the lock file `<root>/<id>.lock`, next to the record. Each `Append` and `Finish` call opens the lock file on its own file descriptor (creating it with mode `0644` when missing), so goroutines of one process and other processes exclude each other. It holds the lock from before it reads the record until after the replacement (or the failure) and releases it (unlock and close) before returning, on every exit path, including the existing errors (`run event exceeds record size limit`, `run summary exceeds record size limit`, an unreadable or corrupt record, a failed write). The lock file is never removed; it is not a record and `List` does not report it.
- Because the kernel drops a flock when its holder ends in any way (SIGKILL included), a lock file left by a dead process never blocks: a later `Append` or `Finish` takes the lock at once.
- The wait for the lock is bounded by the exported constant `durable.RunLockWait = 10 * time.Second`. A call that has not obtained the lock within the wait returns, without reading or writing the record, the error `run record "<id>": lock still held after <wait>` (the ID with `%q`, the wait with `time.Duration.String`), for example `run record "held": lock still held after 300ms`. Waiting may poll with a non-blocking flock; how it waits is the implementation's choice, but it returns the error promptly once the wait has passed (acceptance allows 2 s beyond a 300 ms wait).
- `durable.OverrideRunLockWait(wait time.Duration) (restore func())` is the test seam, like `git.OverrideTimeouts`: until the returned `restore` is called, every `RunStore` in the process waits at most the given positive `wait`. No setting or configuration key changes the wait.
- The run ID is validated before any lock file is created: an invalid ID returns the unchanged `invalid run ID "<id>"` error and creates no file anywhere.
- Records of different run IDs use different lock files and never wait for each other (no store-wide or process-wide lock around the per-ID lock).
- Every `Append` or `Finish` that returns nil is visible in the final record, and the events appear in the order in which the `Append` calls completed (the order they obtained the lock). With more events than the bound, the record holds the newest 32 events and `Omitted` counts the rest, as today.

Unchanged: the record format (`version`, `id`, `events`, `omitted`, `outcome`, `reason`, `evidence`), the bounds (32 events, 65536 bytes), all existing error texts, the temp-file write and syncs, `OpenRunStore`, `Read` (takes no lock: a rename shows the old or the new record) and `List`. The contract suite does not cover `RunStore` and is unchanged. README gains a short "Run records" section stating the lock file, `durable.RunLockWait`, the error text and `durable.OverrideRunLockWait`; the doc comments of `Append`, `Finish`, `RunLockWait` and `OverrideRunLockWait` state the same.

Acceptance builds (`go build -o`) and runs a Go driver that the step file generates in a temporary dot-prefixed folder of the module (removed after each case). Each case works in its own temporary records folder. Helper processes are the driver binary re-executed with `RUN_HELPER` set: `append` (opens a store, waits for a line on stdin, then appends its numbered events and prints its error count) and `hold` (takes `flock(LOCK_EX)` on `<root>/<id>.lock` itself, prints `LOCKED`, and holds it until its stdin closes or it is killed). Cases:
- `goroutines`: 8 goroutines sharing one store append `g<w>-0` .. `g<w>-24` to run `many` at once.
- `processes`: two `append` helpers append `p<k>-0` .. `p<k>-49` to run `shared`, released together.
- `finish-race`: 20 goroutines append `e-0` .. `e-19` to run `fin` while one calls `Finish("fin", "done", "raced", ["attempts/fin"])`.
- `held-then-dead`: with a `hold` helper on `held` and the wait overridden to 300 ms, `Append` and `Finish` each fail after 300 ms to 2.3 s with the lock error and write no record; after the wait is restored (`RunLockWait` reads `10s`) and the helper is SIGKILLed, leaving `held.lock`, an `Append` succeeds in under a second.
- `independent`: with a `hold` helper on `a` and the wait overridden to 5 s, an `Append` to `a` waits while 10 `Append`s to `b` complete; after the helper is released the `Append` to `a` succeeds.
- `error-paths`: with the wait overridden to 300 ms, every existing error of `Append` and `Finish` on run `e` (oversize event, oversize summary, corrupt record, invalid IDs `../escape` and `x.y`) is followed by a call that succeeds, so no path keeps the lock; the folder holds `e.json` and `e.lock`, nothing is created outside it, and the record bytes are today's format.

A retained event tail is judged per writer: every writer's retained events are its newest ones, in the order it appended them, with no stage twice, and the retained events plus `Omitted` equal the number of successful appends.

## Decisions
- Read, change and replace of one run record is serialized per run ID across processes with an advisory lock file next to the record, released on every exit path (source: request)
- The wait for the lock is bounded and its error names the run ID and the wait (source: request)
- Every successful Append or Finish is visible in the final record, events in the order the calls completed; different run IDs do not block each other (source: request)
- Record format, bounds and error texts are unchanged (source: request)

## Source comparison
- Request "Problem" (lost events and summaries overwriting events, unreported): replaced by the per-ID lock around the whole read-change-replace of `Append` and `Finish` (prose, first bullet).
- Request "Need", advisory lock file next to the record released on every exit path: `<root>/<id>.lock` with `flock`, released before every return; scenarios "Every error path releases the lock ..." (folder `["e.json","e.lock"]`) and "A live lock holder ..." (folder `["held.json","held.lock"]`).
- "Bounded wait that returns an error naming the run ID and the wait": `durable.RunLockWait` (10s) and the text `run record "<id>": lock still held after <wait>`; scenario "A live lock holder makes Append and Finish fail after the wait ..." (`run record \"held\": lock still held after 300ms`, `default_wait` `10s`). The 10 s value and the `OverrideRunLockWait` seam are decided here (the request leaves the wait's length open; the seam keeps tests short, following `git.OverrideTimeouts`).
- "Every successful Append or Finish is visible; order of events matches the order in which the calls completed": per-writer newest-tail judgement in the goroutine and process scenarios, and the finish-race scenario.
- "Records for different run IDs do not block each other" and synthetic "Appends to run A and run B in parallel finish without waiting for each other's lock": scenario "Appends to run B finish while an Append to run A waits for A's lock" (`a_still_waiting_when_b_finished` true; A's lock is held by a helper so the test does not depend on timing luck).
- "Existing record format, bounds and error texts are unchanged": scenario error-paths (exact error texts and record bytes); the 32-event bound in every tail scenario; existing `durable/run_store_test.go` tests stay unchanged and passing.
- Synthetic "8 goroutines each Append 25 distinct events ... all 200 events (or, when the event bound is lower, exactly the newest bound events with Omitted equal to the rest), none duplicated": the bound is 32, so scenario "Eight goroutines ..." expects 32 events, `Omitted` 168, sum 200, distinct, newest per writer.
- Synthetic "Two helper processes (the test binary re-executed) append 50 events each ...: 100 events in the final record": with the bound 32 this is 32 events and `Omitted` 68 (sum 100), scenario "Two helper processes ..." (acceptance re-executes the driver binary; the Go test re-executes the test binary).
- Synthetic "Finish racing with 20 Appends: the final record has the Finish outcome and reason and every Append that returned nil": scenario "Finish racing with 20 Appends ..." (outcome `done`, reason `raced`, evidence `attempts/fin`, all 20 stages).
- Synthetic "A lock file left by a dead process does not block a later Append longer than the documented wait; the error names the run ID": with flock the kernel releases a dead holder's lock, so the later `Append` succeeds at once (under 1 s, well inside the wait); the error naming the run ID can only arise while a live process holds the lock, which the same scenario checks first.

## Tests
- Concurrent `Append`s from goroutines lose no event (8 × 25 on one run: 32 events, `Omitted` 168, distinct, newest per goroutine in order): new test in `durable/run_store_test.go` (integration)
- Concurrent `Append`s from two processes lose no event (the test binary re-executed as two helpers, 50 events each: 32 events, `Omitted` 68): new test in `durable/run_store_test.go` (integration)
- `Finish` racing with 20 `Append`s keeps its outcome, reason and evidence and every event: new test in `durable/run_store_test.go` (integration)
- A held lock makes `Append` and `Finish` return `run record "<id>": lock still held after <wait>` after the overridden wait without writing; a lock file whose holder process was killed does not block: new test in `durable/run_store_test.go` (integration)
- Different run IDs do not wait for each other's lock: new test in `durable/run_store_test.go` (integration)
- Every error path of `Append` and `Finish` releases the lock (a later call with a short overridden wait succeeds), invalid IDs create no file, and the lock file is `<root>/<id>.lock` not listed by `List`: new test in `durable/run_store_test.go` (integration)
- The requested behaviour through the public `durable` API in a separate program with helper processes: acceptance scenarios with the generated driver (scenario)
- Record format, bounds and error texts unchanged: existing `TestRunStoreTransitions`, `TestRunStoreBoundsAndErrors`, `TestRunStoreListFiltersEntries` unchanged (existing)
