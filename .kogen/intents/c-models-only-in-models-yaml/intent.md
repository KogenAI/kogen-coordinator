# Read model roles only from the models files

Slug: c-models-only-in-models-yaml
Model: not applicable — LoadConfig reads up to three files once per call and keeps no state between calls; the precedence is a fixed order, not interacting state
Acceptance:
- .kogen/intents/c-models-only-in-models-yaml/acceptance.feature
- features/steps/c-models-only-in-models-yaml__config.js

Model roles live only in the models files: the team file `.kogen/models.yaml` (`project.ModelsPath`) and the host-local `.kogen/local/models.yaml` (`project.LocalModelsPath`). `.kogen/project.yaml` (`project.ConfigPath`) no longer accepts a `models:` key. This is a removal (owner decision 6 Nov 2026, Studio kogen/models-only-in-models-yaml-no-legacy-20261106 r1 and kogen/models-split-rollout-order-20261106 r1). We are in development: there is no legacy read, no fallback and no migration of an old `models:` block.

Today `LoadConfig` merges defaults, the roles `.kogen/project.yaml` names and `.kogen/local/models.yaml`, and does not read `.kogen/models.yaml`; `ParseConfig`, `ReadableConfig` and `RenderConfig` read or write a `models:` block in `.kogen/project.yaml`. Two sources made a fresh Claude-only project silently fall back to the ChatGPT default, and an all-defaults team file could fight explicit roles. All of that is replaced by the rules below.

Rules:
1. `project.ParseConfig(text, file)` (and so `LoadConfig` and `ReadableConfig`, which share its validation) refuses a root `models:` key in the project configuration. The error is a `*sys.Error` with class `environment`, reason `project_config_invalid`, exit 3, Detail `file` (for `LoadConfig` that is `filepath.Join(root, ".kogen/project.yaml")`, as for every other problem of that file), and one line for the key, at the line of the `models:` key. The request requires the line to name `.kogen/project.yaml`, the key's line and "move the model lineup to .kogen/models.yaml"; in the existing `line N: <message>` format of every configuration problem (evidence: project/config.go `configProblems`, lines 299-311) the line is exactly:
   `line <N>: models is no longer read from .kogen/project.yaml; move the model lineup to .kogen/models.yaml`
   The contents under the key are not validated and produce no further lines, as the removed options `shape_workers` and friends are skipped without reading their contents (evidence: project/config.go `validateConfig`, lines 338-340). Other problems of the same file are still reported alongside it, sorted by line as today. Example: in `version: 1\ncommands:\n  checks:\n    - name: test\n      run: 'go test ./...'\nmodels:\n  build: ...` the `models:` key is on line 6, so the line is `line 6: models is no longer read from .kogen/project.yaml; move the model lineup to .kogen/models.yaml` (evidence: project/config.go `configProblems` format, lines 299-311).
2. `project.ReadableConfig(text)` does not apply a `models:` key: it returns every other key it could read (commands, protect) and `Models` equal to `project.DefaultModels()`.
3. `project.LoadConfig(root)` takes every role only from the files, in this order (later wins, per whole role): `project.DefaultModels()`, then `.kogen/models.yaml` when it exists, then `.kogen/local/models.yaml` when it exists. Each role a file names replaces the whole role (no field of an earlier role survives); a role no file names keeps the default. A missing team file keeps the defaults, as today; a missing local file is skipped, as today. Example: team file names shape, build and review as `{executor: claude-code, model: claude-sonnet-5-5, effort: high}` and the local file names only build as `{executor: claude-code, model: claude-opus-5-5, effort: max}`: build is the local role, shape and review the team roles. The effort is given because a claude-code role must name a non-blank model and effort (evidence: project/config.go `externalRole`, lines 542-545).
4. The team file is read and validated by `LoadConfig` with the same schema and validation the local file already has (`parseModelsFile`: root mapping whose only key is `models`, roles `shape`, `build`, `review`, `plan` unknown, executor, provider, base_url and effort rules, `max_rounds` rejected). This file validation is unchanged. A malformed team file fails the load the way `LoadConfig` already fails a malformed local models file: `environment/project_config_invalid` (exit 3) with Detail `filepath.Join(root, ".kogen/models.yaml")` and one `line N: <message>` line per problem (evidence: project/config.go `applyLocal`, lines 179-183). A team file that exists but cannot be read is `environment/project_config_invalid` (exit 3) with detail `read <root>/.kogen/models.yaml: <error>`, the shape `LoadConfig` already uses for an unreadable local file (evidence: project/config.go `applyLocal`, lines 165-174). Files are read in precedence order and the first failure stops the load, as `LoadConfig` already reports `.kogen/project.yaml` before the local files and the local models file before the local checks file (evidence: project/config.go `LoadConfig` and `applyLocal`, lines 144-204; README.md "Host-local lineups and checks", Errors): `.kogen/project.yaml`, then `.kogen/models.yaml`, then `.kogen/local/models.yaml`, then `.kogen/local/checks.yaml`; no Config is returned.
5. `project.RenderConfig(c)` no longer writes a `models:` block, whatever `c.Models` holds: the text ends with the `protect` lines. `project.Template()` likewise ends with its `protect: []` line and has no `models:` line, because `RenderConfig` copies its `models:` block from `Template()`, `RenderConfig(&Config{})` must equal `Template()`, and the template must load with `LoadConfig` (evidence: project/render.go lines 9-29 and 80-82; contract/config_test.go `TestTemplateAndRenderConfig`, lines 251-268; project/config_test.go `TestRenderEmptyConfigEqualsTemplate`, lines 80-86). Both still parse with `ParseConfig`.
6. Documentation describes the one place: `Config.Models`' comment, the package comment of `project/config.go` ("commands, protected paths, models"), `LoadConfig`'s, `RenderConfig`'s, `Template`'s and `ModelsTemplate`'s doc comments, README.md ("Packages" line for `project`, "Opt-in model lineup API" and "Host-local lineups and checks", which today say `LoadConfig` takes models from `.kogen/project.yaml` and does not read the team file) and contract/README.md (`models-lineup`, `config-local-overlay` items and the affected rows).

Nothing else changes: the `commands` (setup, fix, checks, acceptance) and `protect` keys and their errors, the ignored `shape_workers`, `shape_audit`, `shape_decision_check` and `review_material` keys, `old_kogen_config` and `not_initialized`, `.kogen/local/checks.yaml`, `Protected`, `Baseline` and `FormerBaseline` (`.kogen/models.yaml` stays in the approval baseline when present), `LoadModels` (it still requires the team file), `ModelsTemplate`'s text, `DefaultModels`, `Role` and its JSON, and the exit codes of every other error. Add no dependency. This repository's own `.kogen/project.yaml` is not part of this change (it is read by the host's pinned Kogen and is protected).

Existing Go tests that put `models:` in a project configuration (in `project/config_test.go`, `project/intent_test.go`, `contract/config_test.go`, `contract/helper_test.go` fixtures and similar) are updated: role validation cases move to the models file (through `LoadModels` or `LoadConfig` with `.kogen/models.yaml`), and tests of the removed behavior are deleted. The golden files (`project/testdata/golden.json`, `facts-golden.json`, `parity.json`) are regenerated with `go test ./... -update` where their recorded results change, then reviewed; `TestGoldenIsCurrent`'s check that the golden render contains `models:\n  shape:` is replaced by one that fits the new template. Never edit recorded bytes by hand.

## Decisions
- `.kogen/project.yaml` with a `models:` key is refused by `ParseConfig`, `LoadConfig` and every caller of its validation with `environment/project_config_invalid`, exit 3, naming the file, the key's line and "move the model lineup to .kogen/models.yaml"; there is no legacy read (source: request)
- The refusal line is exactly `line <N>: models is no longer read from .kogen/project.yaml; move the model lineup to .kogen/models.yaml`, in the existing `line N: <message>` format, and the contents under the key add no further lines, as removed keys are skipped unread (evidence: project/config.go configProblems lines 299-311 and validateConfig lines 338-340) (source: request)
- `ReadableConfig` returns the readable remainder and keeps `DefaultModels()` for the roles when the text has `models:` (source: request)
- `LoadConfig` roles: defaults < `.kogen/models.yaml` < `.kogen/local/models.yaml`, whole-role replacement, missing team file keeps the defaults (source: request)
- A malformed or unreadable team file fails `LoadConfig` with the existing file validation and in the error shape `LoadConfig` already uses for the local models file, files checked in precedence order with the first failure reported (evidence: project/config.go LoadConfig and applyLocal lines 144-204; README.md "Host-local lineups and checks" Errors) (source: request)
- `RenderConfig` writes no `models:` block; `Template()` drops its `models:` block too, because `RenderConfig` copies that block from `Template()`, `RenderConfig(&Config{})` must equal `Template()` and the template must load (evidence: project/render.go lines 9-29 and 80-82; contract/config_test.go TestTemplateAndRenderConfig lines 251-268) (source: request)
- Config schema comments, `ModelsTemplate`'s comment, README.md and contract/README.md describe the models files as the one place (source: request)

## Source comparison
- Need 1 (refuse `models:` in `.kogen/project.yaml`, class/reason, exit 3, file, line, move text; `ReadableConfig` does not apply it): rules 1–2; scenarios "A models key in .kogen/project.yaml is refused by LoadConfig and ParseConfig" and "ReadableConfig reads the rest and does not apply a models key".
- Need 2 (roles only from defaults, `.kogen/models.yaml`, `.kogen/local/models.yaml`; whole-role; missing team keeps defaults; validation unchanged): rules 3–4; scenarios "The team file decides every role it names", "A team file naming one role keeps the defaults for the others", "The local file replaces only the roles it names over the team file", "Without models files the roles are the defaults", "A malformed team file fails the load with its path and line".
- Need 3 (`RenderConfig` writes no `models:`; schema, `ModelsTemplate`, README and contract files describe the one place): rules 5–6; scenario "RenderConfig and the template write no models block"; documentation through review.
- Need 4 (nothing else changes): boundaries paragraph; rendered text of commands and protect is asserted byte for byte; existing Go and contract tests keep covering checks, setup, fix, acceptance, protect, `Protected`, `Baseline`, `LoadModels`.
- Synthetic acceptance 1–6: scenarios 1, 2, 4 (with 3), 5, 7 and 8, with the literal `executor: claude-code`, `model: claude-sonnet-5-5` and `External()` true; the fixtures add `effort: high` because a claude-code role must name a non-blank effort (evidence: project/config.go externalRole lines 542-545).
- `Template()` is not named in the request; it is changed because `RenderConfig` takes its `models:` block from it and `RenderConfig(&Config{})` must equal it (evidence: project/render.go lines 80-82; contract/config_test.go lines 251-268). The repository's own `.kogen/project.yaml` (which has a `models:` block) is out of scope and unchanged.
