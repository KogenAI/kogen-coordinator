# Provide scoped Studio rule snapshot loading

Slug: coord-studio-rule-snapshots
Model: not applicable — the change is a request/cache/precedence function over one HTTP read; the only state is one verified cache file per scope, whose rules are stated and observed in the scenarios
Acceptance:
- .kogen/intents/coord-studio-rule-snapshots/acceptance.feature
- features/steps/coord-studio-rule-snapshots__driver.js
- features/steps/coord-studio-rule-snapshots__driver/main.go.txt

kogen-coordinator gains one new package `rules` (import path `github.com/KogenAI/kogen-coordinator/rules`) that loads a scoped rule snapshot from the already deployed Studio rules read, so Shape, Build and Review call one producer instead of each implementing authentication, caching and precedence. The Studio read is `studio_workflow rules {workspace_id,product_id,repo}` or authenticated `GET /api/rules?workspace_id=W&product_id=P&repo=R` with `Authorization: Bearer TOKEN`, returning `{product,repo,rules}` where each rule is `{id,revision,scope,topic,text,owner,overrides}`; most-specific scope wins per topic; a missing or invalid token is 401, unknown query keys 400. The change adds no scheduler, no PostgreSQL project, no credential and no change to `.kogen/project.yaml`, `project.LoadConfig`, the approval baseline or any golden file. A project without `.kogen/studio-rules.yaml` is unconfigured and keeps normal standalone execution. The broad header `Depends-on: studio-coord-sets-and-scheduling` is removed by the execution owner on the evidence that the deployed Studio rules read is the only prerequisite; this Intent carries no such dependency and does not mark sets or scheduling complete.

## Public contract (package `rules`)

Configuration: `rules.ConfigPath` is `.kogen/studio-rules.yaml`, a committed team file with these keys only, all required, `version: 1` first: `url` (http or https base URL of Studio), `workspace_id`, `product_id`, `repo`, `token_env` (the NAME of the environment variable that holds the operator-provisioned token; the token itself is never in the file, so a `token` key is an unknown key) and `on_unavailable` (`hold` or `unavailable`). `rules.LoadConfig(root string) (rules.Config, error)` returns `Config{URL, WorkspaceID, ProductID, Repo, TokenEnv, OnUnavailable string}`; an absent file returns the sentinel `rules.ErrNotConfigured`; an unknown, missing or invalid key returns `*rules.Error` with `Class` `environment/project_config_invalid` and a `Reason` naming the file path and the key, never the value.

Loading: `rules.Load(ctx context.Context, root string, opts rules.Options) (*rules.Snapshot, error)` where `Options{Getenv func(string) string; Now func() time.Time; Log func(line string); Client *http.Client}`; every field is optional (defaults `os.Getenv`, `time.Now`, no logging, an `http.Client` whose timeout is the constant `rules.RequestTimeout` = 10 seconds). Unconfigured: returns `nil, rules.ErrNotConfigured` and makes no request and no file. Configured: it always asks Studio first (`GET <url>/api/rules?workspace_id=W&product_id=P&repo=R`, exactly those three query keys, header `Authorization: Bearer <token>` with the token read from `Getenv(token_env)`), so a changed revision affects the next load.

`rules.Snapshot` (JSON tags in parentheses) holds: `Authority` (`authority`, always `advisory`: rule text is data and cannot approve, skip checks or change protected paths; the package exposes nothing that does), `Scope` (`scope`: `{workspace_id, product_id, repo}`), `Rules` (`rules`: the rules in response order, each `rules.Rule{ID, Revision json.RawMessage, Scope, Topic, Text, Owner string, Overrides json.RawMessage}` with tags `{id,revision,scope,topic,text,owner,overrides}`; revision and overrides are preserved exactly as Studio sent them), `ContentHash` (`content_hash`), `RetrievedAt` (`retrieved_at`, UTC, from `Options.Now` at the live retrieval), `Origin` (`origin`: `rules.Origin` `live` or `cached`) and `FallbackReason` (`fallback_reason`, empty when live).

`ContentHash` is `sha256:` followed by the lowercase hex SHA-256 of the compact JSON array of the rules in response order: each rule an object with keys in the order `id, revision, scope, topic, text, owner, overrides`, no whitespace, strings encoded by Go `encoding/json` with HTML escaping disabled.

A live response is valid only when it is a JSON object `{product,repo,rules}` whose `product` equals the configured `product_id`, whose `repo` equals the configured `repo`, whose `rules` is an array, and each rule has non-empty string `id`, `scope`, `topic`, `owner`, a string `text`, a present non-null `revision` and a present `overrides` key; ids are unique and topics are unique (Studio already applies most-specific-scope-wins, so a second rule for one topic is malformed). A valid live response is returned with origin `live` and written as the cache for exactly that scope at `.kogen/local/studio-rules/<sha256 hex of workspace_id, product_id and repo joined with NUL>.json`, containing the Snapshot JSON (a failed cache write does not fail the load). The cache never holds a token.

Failure handling, with `*rules.Error{Class, Reason}` (`Error()` is `Class: Reason`) and these exact reasons:
- Outage (connection failure or timeout, reason `unreachable`; HTTP 5xx, reason `http_<status>`; invalid response, reason `malformed_response`): the last verified snapshot for exactly the same scope is returned with origin `cached`, its original `RetrievedAt`, its `ContentHash` and `FallbackReason` set to the reason. A cache file is verified only if it parses, its `scope` equals the configured scope and its recomputed content hash equals its `content_hash`; otherwise it counts as absent. A malformed response never replaces the cache.
- No valid cache: error with `Class` `rules/hold` or `rules/unavailable` according to `on_unavailable`, `Reason` the outage reason. No snapshot is returned, so nothing is asserted as applied.
- Invalid token or denied (any HTTP 4xx, e.g. 401 and 403, and a missing token variable with no request made, reason `token_missing`): error `Class` `rules/refused`, `Reason` `http_<status>` or `token_missing`. This is not an outage: no cache is read or exposed, whatever it holds.
- `Log` receives, per load, one line `studio-rules: origin=<live|cached> hash=<content_hash> rules=<n> retrieved_at=<RFC3339> fallback=<reason or none>`, or on error `studio-rules: error=<class> reason=<reason>`. No log line, error text, snapshot or file the package writes contains token bytes.

Consumers: Shape, Build and Review call `rules.LoadConfig`/`rules.Load` and decide what to do with the returned snapshot or error; wiring them is the three dependent members' work, not this one. The offline consumer fixture is `rules/testdata/consumer/response.json` (a recorded-shape Studio response for workspace `optimum`, product `kogen`, repo `kogen-shaping`: top-level keys exactly `product`, `repo`, `rules`, at least one rule, each rule with exactly the seven keys) and `rules/testdata/consumer/snapshot.json` (the Snapshot JSON that loading it live yields with `Now` fixed at `2026-11-16T10:00:00Z`).

README gains a `Studio rule snapshots` section stating the package, `.kogen/studio-rules.yaml` and its keys, that `token_env` names an operator-provisioned secret reference and no credential is stored, the cache location, the failure classes, the read contract (`studio_workflow rules`, `GET /api/rules`, Studio source `d105f3cbf6d68daebfc473bdb032a81d2ec7bc0c`, `README.md line 1702`) and that live credentials/provisioning stay with their existing owner. `contract/` gains `rules_test.go` pinning the exported API and the fixture.

## Decisions
- A new rules package in kogen-coordinator is the one producer; configuration is a separate committed .kogen/studio-rules.yaml so project.yaml, the approval baseline and goldens are untouched (decision: D1, round 1) (evidence: README.md; .kogen/project.yaml) (assumption: The request leaves open whether config lives in project.yaml; a separate file was chosen.) (source: request)
- Token is referenced only by environment-variable name token_env; a literal token key is rejected without echoing the value (decision: D2, round 1) (evidence: README.md) (source: request)
- Studio response is authoritative for most-specific-scope precedence; duplicate topics, wrong product/repo or missing fields are malformed; scope values and overrides type kept opaque (decision: D3, round 1) (assumption: Live scope values and overrides type are not fixed by the request.) (source: request)
- Outages (unreachable, 5xx, malformed) use only a verified same-scope cache and report origin cached with reason; 4xx and missing token never touch a cache (decision: D4, round 1) (evidence: README.md) (source: request)
- Unavailable policy on_unavailable hold|unavailable yields error classes rules/hold and rules/unavailable (decision: D5, round 1) (assumption: The owner's exact named outcomes are assumed.) (source: request)
- Acceptance uses a generated Go driver against a loopback fake endpoint with synthetic tokens; controls.json deferred (decision: D6, round 1) (evidence: features/steps/coord-run-store-concurrent-append__driver.js) (assumption: Driver was not compiled against an implementation during shaping.) (source: request)
- The default HTTP client timeout is the constant rules.RequestTimeout of 10 seconds, with no setting (decision: D7, round 1) (assumption: The request fixes no timeout; 10 seconds is chosen as a bounded wait.) (source: request)

## Source comparison
- Request: Studio read contract `{product,repo,rules}`, rule fields `{id,revision,scope,topic,text,owner,overrides}`, `GET /api/rules` query keys, Bearer token, 401/400: addressed by the public contract and the fake endpoint that enforces exactly those keys and the token (scenarios live, refused).
- Request: dependency clarification removing `Depends-on: studio-coord-sets-and-scheduling`: addressed; the Intent has no such dependency and keeps the producer scope, native approval, checks and secret handling unchanged.
- Request: explicit configuration, unconfigured standalone: addressed by `.kogen/studio-rules.yaml` and `ErrNotConfigured` (scenarios unconfigured, config).
- Request: provenance (IDs, revisions, hash, scope, retrieval time, live/cached, reason): addressed by Snapshot fields (scenarios live, cached-outage, fixture).
- Request: changed revision, cached outage same scope, wrong scope, invalid token, absent cache, malformed, hash: scenarios changed-revision, cached-outage, wrong-scope, refused, absent-cache, malformed, tamper.
- Request: no token bytes in logs: scenario no-token-bytes. No network dependency: loopback fake only.
- Request: rule text cannot override approval/checks/protection: `authority: advisory` observed on a rule whose text says to skip approval (scenario live); the package exposes nothing that changes approval, checks or protection.
- Request: exact dependency/pin evidence and offline consumer fixture: README section and `rules/testdata/consumer/` (scenarios pins, fixture).
- Request: schema changes, new scheduler, standalone PostgreSQL project, credentials, consumer wiring: omitted by design.
