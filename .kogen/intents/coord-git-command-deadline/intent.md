# Stop repository Git commands at a deadline

Slug: coord-git-command-deadline
Model: not applicable — each Git command is an independent subprocess with its own deadline; nothing persists between calls
Acceptance:
- .kogen/intents/coord-git-command-deadline/acceptance.feature
- features/steps/coord-git-command-deadline__deadline.js

Every Git command the `git` package runs for a repository gets a bounded wall time. Today `Repo.exec` (git/git.go), which runs every `status`, `rev-parse`, `diff`, `ls-files`, `ls-tree`, index, `hash-object`, `update-index`, `commit-tree`, `update-ref`, `config`, `log` and other call, waits on `cmd.Run()` with no limit. The `cat-file --batch` blob stream (`openBlobs`/`blobStream.copy` in git/snapshot.go) blocks on its reads with no limit. The `git commit` and `git hook run` calls in git/commit.go (`Commit`, `CommitPaths`, `CheckCommitMsg`) run through `sys.Session.Run` without `Options.Timeout`. A stuck hook, a lock held by a dead tool or a hung filesystem therefore blocks a whole Build silently. After this change, each command stops at its bound. The caller then receives an error that names the command and the bound and says that it timed out.

Interface (package `git`, all exported):
- `const CommandTimeout time.Duration = 10 * time.Minute`: the bound of every command run through the package's runner (`Run`, `RunEnv`, `OK`, `OKEnv` and every internal call), and of each read from the blob stream.
- `const CommitTimeout time.Duration = time.Hour`: the larger bound for the commands that run the user's commit hooks: the `git commit` of `Commit` and `CommitPaths`, and the `git hook run --ignore-missing commit-msg` of `CheckCommitMsg`.
- Both constants have doc comments that state these bounds. A new README section "Git command deadlines" documents the two bounds, which commands each one covers, the error and the seam.
- `func OverrideTimeouts(command, commit time.Duration) (restore func())`: the test seam. Until `restore` is called, the effective bounds of every Repo in the process are `command` and `commit` instead of the constants. `restore` puts back the values that were in effect before the call. Callers pass positive durations. The values are read when each command starts, safely for concurrent use (`go test -race`).
- `type TimeoutError struct { Args []string; Timeout time.Duration }`, with `Error()` exactly `"git " + strings.Join(Args, " ") + " timed out after " + Timeout.String()`. `Args` are the first at most four of the caller's Git arguments, excluding the `-c core.fsmonitor=false` prefix that a read-only Repo adds. `Timeout` is the effective bound. The text never contains environment values (base or extra `KEY=VALUE`), stdout or stderr. Examples: `git status --porcelain timed out after 1.5s`; `git log -1 --format=%s --no-color timed out after 1.5s` (from `log -1 --format=%s --no-color HEAD`).

Behavior:
- Runner (`Repo.exec`): each command starts in its own process group. When the command bound passes, the whole group is killed with SIGKILL, so the Git process and its children (hooks, `sleep`, ...) all stop. The runner waits for the process and returns `*TimeoutError`. `Run`/`RunEnv` return `Result{Status: -1}` with that error; `OK`/`OKEnv` and the internal callers return it as their error. A pipe held open by a process outside the group may delay the return by at most 1 second (`exec.Cmd.WaitDelay`). The call returns within the bound plus 2 seconds.
- Blob stream: `git cat-file --batch` also starts in its own process group. Each read (`blobStream.copy`: request, header and content of one blob) must finish within the command bound, measured from its request. When the bound passes, the group is killed, the stream is closed (its process waited for), and the read returns `*TimeoutError{Args: ["cat-file", "--batch"]}` itself, without the `git cat-file <oid>: ...` wrapping or stderr. `Materialize` and `RestoreTree` return that error unchanged. Bounding each read rather than the whole stream lets a large materialization run as long as every blob keeps arriving.
- Commit hooks: `Commit`, `CommitPaths` and `CheckCommitMsg` pass the commit bound as `sys.Options.Timeout`. When `sys.Result.TimedOut` is set (kogen-loop has already terminated and joined the command's process group), they return `*TimeoutError` with Args `["commit", "-q", "-F", <message file>]` or `["hook", "run", "--ignore-missing", "commit-msg"]`. In that case `Commit` first undoes a commit that landed anyway, as it already does after an interrupt (`undoIfLanded(spec.Start)`). `CommitPaths` unstages its paths as on any other failure. Other `sys.Run` errors are returned as today.
- `Open`/`OpenReadOnly`: a repository discovery (`rev-parse --show-toplevel`) that times out returns the `*TimeoutError`, not `environment/not_a_git_repo`. Methods without an error result (`Root`, `Head`, `Identity`, `CanCommit`, `Show`) treat a timed-out command like any other failed command, as they do today.

Unchanged: the arguments, environment, binary resolution, forbidden-command refusal and revision checks of every command. Commands that finish inside their bound keep their exit statuses (including 128+signal), complete stdout and stderr, `CommandError` type and text, and the existing `sys.Error` results of `Commit`, `CommitPaths` and `CheckCommitMsg`. The `ps` commands in git/lock.go and project/facts.go are not Git commands and stay unbounded. Lock files that a killed Git leaves behind (for example `index.lock`) are not cleaned up. No setting or configuration key is added. The contract suite is not changed: every addition is new API.

## Decisions
- Every Git command the coordinator runs for a repository, including status, rev-parse, diff, index and commit calls and the `cat-file --batch` blob stream, has a bounded wall time. (source: request)
- At the bound, the process and its children are terminated, and the caller receives an error that names the command by its first arguments (at most four), the bound and that it timed out, and never contains environment values. (source: request)
- Normal commands, their exit statuses and their outputs are unchanged. (source: request)
- Commits and commit hooks use the larger bound `CommitTimeout` (1 hour); every other command and each blob-stream read uses `CommandTimeout` (10 minutes). Both are named, documented constants that `OverrideTimeouts` overrides for tests. (source: request)

## Source comparison
- Addressed: "Every Git command ... (status, rev-parse, diff, index and commit calls, the `cat-file --batch` blob stream)" maps to the runner bound (`Repo.exec`), the per-read blob-stream bound and the commit bound on the `sys.Run` calls in git/commit.go, which together cover every Git process the package starts.
- Addressed: "the process and its children are terminated" maps to killing the command's own process group. The fake and hook in acceptance keep a background `sleep 600` child, and "no process of the hanging fake or hook remains" checks both recorded pids.
- Addressed: "error that names the command (its first arguments, never environment values), the bound and that it timed out" maps to `*git.TimeoutError` and its exact text. Acceptance pins `git status --porcelain timed out after 1.5s`, the four-argument cut `git log -1 --format=%s --no-color timed out after 1.5s`, `git cat-file --batch timed out after 1.5s` and `git commit -q -F <message> timed out after 1.5s`.
- Addressed: "Normal commands, exit statuses and outputs are unchanged" maps to the exit-1 and 1 MiB scenarios and to the existing git and contract tests, which must pass unchanged.
- Addressed: "Long commands that legitimately run longer (commit with hooks) use a larger documented bound" maps to `CommitTimeout`. One scenario shows that a pre-commit hook sleeping 2.5 s commits under a 1.5 s command bound and an 8 s commit bound; another shows that a hook that never returns stops at the 1.5 s commit bound under an 8 s command bound, with HEAD unchanged.
- Addressed: "the bounds are named constants and can be overridden by a test seam" maps to `CommandTimeout`, `CommitTimeout` (pinned as `10m0s` and `1h0m0s`) and `OverrideTimeouts`.
- Addressed: synthetic "fake git earlier on PATH that sleeps far past the bound: returns within bound plus 2 s with an error containing 'timed out', the command name and the bound; no process of the fake remains" maps to the two hanging-runner scenarios. They also require that the call took at least the bound.
- Addressed: synthetic "the same fake started through the blob stream: the read returns the same timed out error and the stream is closed" maps to the Materialize scenario, whose fake hangs only in `cat-file`.
- Addressed: synthetic "fake that exits 1 with stderr text: status and stderr are returned exactly as today, with no timeout error" maps to the Run scenario (status 1, stdout `partial out\n`, stderr `fatal: fake failure\n`) and the OK scenario (`git status --porcelain failed (status 1): fatal: fake failure`).
- Addressed: synthetic "fake that prints 1 MiB and exits 0 inside the bound: the output is complete" maps to the scenario that checks 1048576 bytes and their SHA-256. The fake pauses 0.5 s between halves.
- Addressed: synthetic "the error text never contains the environment values passed to the command" maps to the base variable `KOGEN_DEADLINE_SECRET=base-secret-7f3a` and the extra `GIT_AUTHOR_NAME=extra-secret-91c2`. The hanging fake echoes both to its stderr, so an error text that leaked stderr or the environment would fail.
- Decided here (not in the request): the 10-minute and 1-hour values, the four-argument cut, `Result.Status` -1 on a timeout, the per-read blob-stream bound, `CheckCommitMsg` using the commit bound, the undo of a commit that landed before its timeout, and `Open` returning the timeout error.

## Tests
- A runner command past the command bound is killed with its process group and returns `*TimeoutError` "git <first four args> timed out after <bound>" within the bound plus 2 s, with `Run` Status -1, no environment value in the text and no process of the fake left: add a git package test with a fake git first on the Repo's PATH that hangs with a background child, using `OverrideTimeouts` (integration)
- A read-only Repo's timeout names the caller's arguments without the `-c core.fsmonitor=false` prefix: assert `Args` in the same test through `Observing()` (integration)
- A blob-stream read past the bound returns the `*TimeoutError` for `cat-file --batch`, closes the stream and leaves no process: add a `Materialize` test with a fake that hangs only in `cat-file` (integration)
- Commands that finish inside the bound are unchanged: add fake-git cases for exit 1 with stderr (Result and `CommandError` as today) and for 1 MiB printed in two halves (complete output); existing git and contract tests pass unchanged (integration)
- Commit uses the commit bound: a pre-commit hook slower than the command bound commits; a hanging pre-commit hook returns `*TimeoutError` with HEAD unchanged; a hanging post-commit hook returns it with the landed commit undone (integration)
- `CheckCommitMsg` and `CommitPaths` stop a hanging hook at the commit bound: add git package tests with a hanging commit-msg hook and a hanging pre-commit hook that assert the returned `*TimeoutError` and its Args (integration)
- `Open` reports a discovery timeout as the timeout: add a git package test with a fake git that hangs on `rev-parse` asserting `Open` returns the `*TimeoutError`, not not_a_git_repo (integration)
- The bounds are 10m0s and 1h0m0s, the seam overrides them, and the exported API produces the timeout, failure, output and commit outcomes end to end: the acceptance scenarios (scenario)
